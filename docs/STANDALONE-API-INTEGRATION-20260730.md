## 结论

压缩包不是可直接嵌入当前前端的单一工具，而是一套较早的 Spring Boot 与静态页面应用。当前云发布已经具备更完整的项目、报价、订单、媒体筛选、GEO 联动和审计链路，因此没有覆盖现有代码，也没有把旧应用作为第二套后端并行部署。

本轮吸收了旧工具中仍有价值的管理思路：

- 客户 API 与访问日志需要独立管理；
- 媒体检索、记者检索、报价、下单和状态回执必须分能力登记；
- 供应商接口要登记环境、鉴权、路径、限流、超时、重试和数据范围；
- 外部能力必须有授权、沙箱和生产验收状态。

这些能力已合并到当前管理员专属的“接口管理”页面和第 33 号数据库迁移中。接口配置只保存凭据环境变量名称，不保存令牌明文；配置检查不向任意外部地址发请求。

## 未直接导入的内容

- 旧应用的完整 Java 工程、静态页面、构建产物和 Git 元数据；
- 旧配置文件中的默认凭据或疑似密钥；
- 未经过当前权限、字段和异常协议验收的外部接口实现；
- 与当前四项独立服务边界冲突的订单或产品逻辑。

## 后续真实联调

逐家供应商取得合同和书面授权后，在受控分支中为该供应商编写专用适配器，完成字段映射、地址白名单、签名、限流、超时、重试、回执、对账和异常处理测试。通过沙箱与生产验收后，管理员才能把对应配置标记为可用。
