# 发布会媒体候选状态完整性 QA（2026-07-31）

## 结论

本轮修补已把新闻发布会项目中“拟邀媒体候选”的推进过程收敛为可核验的状态链：候选、待邀约确认、已发出邀请、已回复／确认到场／婉拒／暂不推进。客户仍只看到对履约有意义的进度；运营侧才能登记跟进说明。此次验证覆盖源码、本机演示库、干净库、隔离生产等价空库和桌面／移动端页面，但不构成真实媒体邀请、外部数据接入或生产上线证明。

## 问题与影响

原更新入口只校验操作角色，未要求客户端携带当前状态，也没有在服务层锁定候选行。因此运营人员可以把 `CANDIDATE` 直接更新为 `ATTENDING`，并且并发页面可能覆盖较新的进度。这会把“候选名单”错误记录为到场事实，影响项目审计、客户可见进度和后续邀请安排。

## 修补范围

| 层面 | 已完成的处理 |
|---|---|
| API | `UpdateConferenceMediaCandidateRequest` 新增必填 `expectedStatus`。服务端锁定候选行后再比对当前状态；陈旧页面提交返回 `409 CONFERENCE_MEDIA_CANDIDATE_STATE_CHANGED`。 |
| 业务规则 | 仅允许 `CANDIDATE → READY_TO_INVITE → INVITED → RESPONDED／ATTENDING／DECLINED`，或在允许阶段进入 `NOT_PROCEEDING`。`DECLINED`、`ATTENDING`、`NOT_PROCEEDING` 为终态；结果状态必须填写联系记录。 |
| 数据库 | 新增 `41-conference-media-candidate-state-integrity.sql`。三项约束校验状态、时间线和结果说明；触发器拒绝跳级、回退和已登记邀请／回复时间的改写。 |
| 客户字段边界 | 客户项目详情仍不返回候选内部编号、候选键、媒体／记者原始标识、操作说明、跟进记录或运营人；客户可看到结果状态与必要时间点。 |
| 页面交互 | 运营页面只显示合法下一步；终态候选隐藏状态下拉与“保存进度”，显示“邀约结果已记录，状态已锁定”。负责人和时间线文字颜色同步提高对比度，通过无障碍扫描。 |

## 存量迁移边界

迁移执行前已对本机演示库备份：

- 文件：`artifacts/database-backups/winpress-pre-schema41-20260731-134730.dump`
- SHA-256：`9AA45574BE920FC2EE6DE7D3FED5C56D0ADC88403723A636E0968AFF3CC27C22`

迁移先检查：

- 候选／待邀约确认不得已有邀请或回复时间；
- 已邀请必须有邀请时间，回复／婉拒／到场必须有邀请与回复时间；
- 邀请和回复时间不得倒序；
- 结果状态必须有可读的跟进说明。

发现矛盾时脚本会停止。它不补写邀请、回复、到场、联系人、媒体报道或其他履约事实；生产存量处理必须由业务方按可核验材料逐条决定。

## 不在本轮结论内

- 牛媒或其他外部媒体／记者数据的正式授权、字段范围、令牌、限流、沙箱和生产联调；
- 真实媒体邀请、采访、到场、报道或供应商履约；
- 生产域名、TLS、监控告警、备份保留和灾备恢复演练；
- 存量 `WRITING_AND_PUBLISHING` 的映射、迁移、归档或删除。

这些事项仍须按有效 PRD、书面授权、合同和生产验收材料单独推进，不能由本机演示数据或本轮回归替代。
