# Schema 迁移台账 QA（2026-07-31）

## 本轮范围

本轮补齐数据库结构变更的可追溯基线。问题不在业务功能缺失，而在已有编号迁移虽已执行、数据库中却没有可审计的迁移台账：原健康检查只能确认部分结构存在，不能证明当前结构由哪一份已核验基线得来。

本轮只处理本机演示环境与隔离冷启动验证，不连接外部媒体数据、供应商接口或生产环境，也不发布任何真实履约结论。

## 变更设计

- 新增 `schema_migration_ledger`，保存迁移版本、脚本名、接口合同版本、应用方式、核验引用、应用时间与应用主体。
- 新增 `trg_schema_migration_ledger_append_only`；任何更新或删除既有台账记录都会被数据库拒绝。
- 新迁移为 `database/36-schema-migration-ledger.sql`。它先核验 schema 35 的核心表、28 项发布治理证据项和既有完整性触发器，再写入唯一一条基线记录：
  - `migration_version=36`
  - `script_name=36-schema-migration-ledger.sql`
  - `release_contract=winpress-v4.2.25-20260731`
  - `apply_mode=BASELINE`
  - `verification_reference=SCHEMA35_STRUCTURAL_BASELINE_20260731`
- 不倒灌或伪造 1—35 的历史执行记录；后续迁移应以新的 `FORWARD` 记录追加。
- 健康接口必须同时核验台账表、上述基线记录和追加式保护触发器，成功时返回 `schemaVersion=36`、`apiContractVersion=winpress-v4.2.25-20260731`。

## 备份与本机迁移证据

迁移前已导出 PostgreSQL custom 格式备份，未覆盖原库：

- 文件：`database/backups/winpress-commercial-pre-schema36-20260731-021923.dump`
- 大小：`2,838,007` bytes
- SHA-256：`AC7F8035D7A7A79271E64BC718FAF7841F7D9E69F35056D0563DF97B8A367150`

随后在本机 `winpress_commercial` 演示数据库执行迁移。回读确认台账仅有上述一条基线记录；对该记录的 `UPDATE` 已被追加式触发器拒绝，原核验引用保持不变。

同一迁移又从当前源码重复执行一次：`INSERT 0 0`，台账仍为一条完全匹配的版本 36 基线记录，追加式触发器仍存在。这证明该基线迁移可以重复检查，不会生成第二条记录。

## 回滚边界

本迁移为追加式结构变更，不应在运行库中直接删除台账记录或触发器来“回滚”。如需恢复到迁移前状态，应在受控环境使用上述迁移前备份恢复到独立实例，完成业务与健康检查后再按维护流程切换；本轮未执行任何破坏性回滚。
