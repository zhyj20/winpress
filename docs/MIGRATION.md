# 迁移说明

## 旧站审查结果

旧站采用静态 HTML 与单体 Spring 服务混合结构，数据库 18 张表，主要覆盖媒体清单、报价、工单和临时运营审批。缺少以下业务对象：

- 内容撰稿任务与稿件版本
- 客户确认版本
- 三类发布任务及各自执行记录
- 既有稿件锁定安排的存量兼容记录（当前客户入口不开放新建）
- 传播监测、成果核验和结算
- 数据库角色权限关系

旧后端还存在通配跨域、默认 API 密钥、配置文件明文运营口令和内存运营会话。

## 媒体数据迁移

源数据：22,780 条 `media_item`。

迁移处理：

| 检查项 | 结果 | 处理 |
|---|---:|---|
| 媒体编号重复 | 0 | 直接生成稳定渠道编号 |
| 媒体名称缺失 | 0 | 无需修复 |
| 客户价格无效 | 0 | 全部迁移 |
| 成本或同步时间缺失 | 420 | 渠道和报价标记为 `REVIEW_REQUIRED` |
| 地区缺失 | 0 | 全部保留 |
| 分类缺失 | 0 | 全部保留 |
| 收录说明缺失 | 8,385 | 使用统一的媒体审核说明，不推测收录结果 |
| 上游资源标识重复 | 94 组 | 不作为新库唯一键；使用旧媒体编号生成唯一来源引用 |

新库中，旧媒体数据写入 `publish_channel` 和 `channel_quote`。客户接口只查询 `ACTIVE` 渠道，并通过字段白名单隐藏成本、来源引用和内部信息。

## 运行迁移

Docker 首次初始化按建表、基础种子数据、品牌案例数据、媒体导入、公开字段规范化的顺序执行。导入脚本使用临时表，可重复执行；渠道按 `channel_no` 更新，报价按 `quote_no` 去重。

存量 PostgreSQL 数据库还需按顺序执行：

1. `05-separate-writing-from-media-pr.sql`：保留媒体邀请业务，同时把内容撰稿任务字段调整为写作口径。
2. `06-onsite-writing-product.sql`：增加服务天数、写手人数、980 元固定单价、基础金额、现场联系人、交付要求和就近匹配规则。

`06` 对旧需求补入安全默认值，不会把既有远程撰稿订单误改为现场采写。

3. `07-news-conference-replaces-owned-channel.sql`：建立新闻发布会项目、统筹事项和媒体候选清单。
4. `08-niumedia-media-discovery.sql`：扩展媒体候选公开属性，不写入上游授权信息。
5. `09-pricing-management.sql`：建立报价调整记录和渠道筛选索引；上线报价管理接口前必须执行。
6. `10-brand-case-demo-data.sql`：增加四个品牌案例账号与八个项目，覆盖现场采写、稿件审核、媒体邀请、新闻发布会、直编发稿、结果核验和结算。脚本使用稳定业务编号并可重复执行。
7. `11-v4_1-product-core.sql`：增加服务价目、写手档案与派单、媒体主体与联系人、对客渠道商品、发布计划与计划项；为发布任务补入计划项来源，为稿件锁补入版本与到期时间，并为人工调价增加成本价审计字段。
8. `12-media-invitation-without-manuscript.sql`：允许媒体邀请从活动简报直接创建，发布计划与任务的稿件引用改为可空；当前 V4.2 客户流程只要求直编发稿校验已确认稿件版本，旧有锁定字段仅保留存量兼容。
9. `13-conference-progressive-intake.sql`：将发布会改为标题、联系人、联系电话三项必填，其余资料允许后补。
10. `14-supplier-orders-and-conference-workbench.sql`：增加发布会阶段字段、供应商、渠道关系、供应商订单、状态历史和商务咨询。
11. `15-niumedia-reporter-and-multi-invitation.sql`：增加媒体与记者候选统一标识、记者公开字段和图片字段；允许同一媒体邀请计划使用同一个执行通道创建多个不同邀请对象，同时继续限制直编计划重复选择同一渠道。
12. `16-media-partnership-inquiry.sql`：增加媒体合作申请咨询类型；仅用于商务审核，不授予平台接入、报价、结算或发布权限。
13. `17-local-demo-writing-assignment.sql`：仅为固定的本机演示任务 `REQ-DEMO-002` / `EDT-DEMO-002` 补齐一条待匹配云采写派单记录。脚本可重复执行，不更改表结构，也不会作用于其他项目；不得把它当作生产数据迁移使用。
14. `18-service-intake-tasks.sql`：为媒体邀请（`MEDIA_PR`）和直编发稿（`DIRECT_PUBLISHING`）建立一项目一条的服务受理任务；既有开放项目会按是否已分配负责人回填为“待受理”或“处理中”。该迁移不改写价格、供应商映射、上游数据或历史执行记录。
15. `19-activity-project-linkage.sql`：为同一活动下的独立服务增加可选根项目关联。新建服务仍分别生成需求、项目、任务和订单，分别计价；脚本不把既有项目合并、不改写历史价格或供应商记录。
16. `20-direct-manuscript-source.sql`：为直编发稿项目复制客户已确认稿件时保留来源关联。复制后仍生成新的稿件和版本，不复用原稿件行、不合并项目、任务、订单或计价；只有服务端通过客户与组织范围校验的已确认版本可作为来源。
17. `21-manual-media-invitation-pending-verification.sql`：允许人工补充的 `MEDIA_PR` 候选名单在项目核验前暂不绑定执行渠道。它不导入外部目录、报价或供应商，不生成供应商订单，也不代表已向媒体发出邀请。
18. `22-service-intake-title-integrity.sql`：修复历史数据中已被问号替换的服务受理标题，并建立非空、非纯问号标题约束。修复仅依据既有服务类型恢复服务阶段名称，不推测或补写原始媒体、渠道、供应商、成本或价格。
19. `23-settlement-transaction-ledger.sql`：建立有凭据的收款、退款、贷项、借项与核销台账，并保留作废记录。迁移不补写历史交易，结算状态也不再自动制造实收金额。
20. `24-requirement-idempotency.sql`：为客户需求增加请求标识、内容摘要及同一客户范围内的唯一约束。历史需求保持空值；新请求只有在服务端校验后写入，同一标识与同一内容的重试返回原项目，不重复创建后续记录。
21. `25-task-acceptance-integrity.sql`：固化发布任务、媒体邀请和成果链接状态约束，并为同一任务的同一成果链接建立唯一索引。客户验收由服务端锁定任务、核验成果后原子完成；验收后的任务不能回退、重复提交成果或重复产生验收事实。
22. `26-channel-quote-integrity.sql`：校验直编渠道客户价大于零、成本价非负且不高于客户价、报价有效期顺序和允许状态；同一渠道只允许一条 `ACTIVE` 报价。应用调价事务按渠道编号稳定加锁，避免首次报价或重叠批量调价并发产生多条有效价格。
23. `27-media-invitation-progress-integrity.sql`：把已有媒体邀约事实与发布任务、计划和项目状态对齐；拒绝或不再推进使用 `NOT_PROCEEDING` 终态，不能补录发布成果。确认计划后服务受理阶段结束，但不据此声称已联系媒体或已经发布。
24. `28-publish-task-terminal-integrity.sql`：在数据库层保护已完成、客户已验收和媒体不再推进的任务终态；供应商订单或其他后台旁路只能更新自身记录，不能把客户已确认事实重新打开。迁移不生成成果或履约事实。
25. `29-publish-plan-idempotency.sql`：为发布计划增加请求标识、内容摘要及同一项目和创建人范围内的唯一约束。历史计划保持空值；同一标识和相同内容的重试返回原计划，同一标识不能改作另一份计划。迁移不生成媒体选择、任务、订单、价格或供应商事实。
26. `30-settlement-transaction-idempotency.sql`：为结算交易增加请求标识、内容摘要及同一结算单范围内的唯一约束。历史交易保持空值；同一标识和相同内容的重试返回原交易，同一标识不能改作另一笔收款、退款、调整或核销。迁移不生成任何财务或履约事实。
27. `31-batch-quote-adjustment-idempotency.sql`：建立批量调价请求批次，并把每条调价明细关联到批次。同一管理员的请求标识只能绑定一组渠道、比例、有效期、条款和原因；完成批次重试返回原结果，不以已调价格再次计算。迁移不生成或改写任何渠道报价、成本、供应商或外部数据。
28. `32-publish-plan-service-integrity.sql`：建立发布计划与项目服务类型的一致性保护。媒体邀请计划只能属于媒体邀请项目，直编发稿计划只能属于直编发稿项目；项目、需求或计划归属变更也不能绕过边界。已有历史错配记录不被改写，但客户侧不再显示，也不能继续确认生成任务或订单。
29. `33-supplier-api-connections.sql`：建立管理员专用的供应商接口配置、上线验收门禁和历史组合服务审核结构。接口配置只保存凭据环境变量名，不保存密钥值；外部媒体、真实履约、法律信任、生产运维和历史组合五项门禁默认均为待验收。存量 `WRITING_AND_PUBLISHING` 只登记待人工审核，不自动拆单、迁移、归档或删除。
30. `34-open-api-management.sql`：将独立 API 工具的客户系统接入能力纳入云发布管理平台。它建立接入应用、仅保存哈希的访问密钥、请求受理回执和访问摘要；应用启用前须完成授权、沙箱及生产验收门禁。脚本不导入旧工具数据库、演示密钥、供应商配置、外部媒体数据或历史订单，也不自动创建组合服务。
31. `35-release-governance-and-evidence.sql`：把五项总关卡拆为 28 项必备证据，只有逐项核验及运行配置同时满足时才允许通过。供应商订单在“已提交”及以后状态必须写明人工/API 履约方式和提交凭据；API 履约还须具有外部订单号。新建组合服务直接拒绝，存量组合服务只有匹配到已批准的人工决定后才允许转换；脚本不自动拆单、改价、归档或删除。
32. `36-schema-migration-ledger.sql`：为已核验的 schema 35 建立追加式迁移台账基线，健康检查据此确认当前结构来源。它不回填、猜测或伪造历史脚本执行记录，不写入业务数据、凭据、供应商、外部媒体或履约事实；后续迁移必须以新的 `FORWARD` 记录追加。
33. `37-media-pr-result-integrity.sql`：在既有结构台账基线上追加媒体成果事实链门禁。所有完成态发布任务必须已有已核验成果；`MEDIA_PR` 任务还必须先记录已发送的邀请并在结果提交时转为 `REPORTED`。安装前只核验存量矛盾，发现问题即停止，绝不补造邀请、报道、成果或验收事实。
34. `38-writing-assignment-slot-schedule-integrity.sql`：为云采写增加逐写手名额和服务时段。数据库使用排他约束拒绝同一写手的重叠已确认档期；父派单只在全部所需名额确认后进入 `ACCEPTED`。迁移只回填已有单写手事实；若活跃旧派单缺少真实写手、服务时间，或已确认多人派单无法还原名额，脚本会停止等待业务确认，绝不虚构写手、排班或接单记录。
35. `39-writing-assignment-radius-integrity.sql`：将已配置的写手服务半径落实为活跃名额约束。半径必须非负；写手半径非空时，`OFFERED`、`ACCEPTED` 名额必须有人工核验距离且不得超出半径。下调半径若会导致既有活跃名额越界，数据库会拒绝。迁移先检查存量矛盾，发现缺距离或越界即停止，不定位、不推算、不填补历史距离，也不改写订单、价格、排班或履约事实。
36. `40-conference-work-item-state-integrity.sql`：固化新闻发布会统筹事项的完成时间、合法状态迁移与终态保护。已完成事项和已完成发布会项目不能重新打开；发布会项目进入完成态前，全部统筹事项必须已经完成。迁移先检查“状态与完成时间矛盾”以及“项目已完成但仍有未完成事项”的存量记录；发现矛盾即停止，等待业务方基于可核验历史资料逐条修复，绝不补写完成时间、事项状态、项目状态或履约事实。
37. `41-conference-media-candidate-state-integrity.sql`：固化发布会候选名单的推进顺序、邀请／回复时间线与终态保护。候选须依次经待邀约确认、已邀请后才可记录回复、到场、婉拒或不再推进；终态不可被普通更新改写，结果状态必须留存跟进说明。迁移先检查状态、时间线和说明的存量矛盾；发现问题即停止，等待业务方基于可核验资料逐条修复，绝不补造邀请、回复、到场、联系人或履约事实。

案例迁移只用于本地演示或经授权的测试环境。上线前应决定是否保留这些账号；如保留，必须修改默认密码并继续显示“案例演示”标识。

当前变更以 `schema.sql` 与顺序迁移脚本为准：`schema.sql` 已包含服务受理任务、活动根项目关联、直编稿件来源关联、结算交易结构、需求提交幂等约束、任务验收、渠道报价、媒体邀约进度、任务终态、发布计划、结算交易、批量调价幂等、发布计划服务边界、供应商接口配置、上线验收门禁、历史组合审核、开放 API 管理、逐项发布证据、追加式迁移台账、云采写名额／档期／半径保护及发布会统筹事项、候选名单状态保护；存量库须执行迁移 `18` 至 `41`。迁移 `17` 只补齐本机演示数据，不能纳入生产发布。迁移 `22` 至 `41` 分别让运行时健康检查确认服务受理标题完整性、交易凭据约束、下单幂等结构、客户验收完整性、有效报价唯一性、媒体邀约终态边界、数据库终态保护、发布计划幂等、结算交易防重、批量调价批次、发布计划服务一致性、供应商接口验收门禁、开放 API 密钥／回执、逐项证据／历史组合边界、已核验结构台账、媒体成果事实链、写手名额／档期冲突、服务半径／人工距离及发布会事项、候选名单状态／时间线保护。`winpress_full.sql` 仍是历史快照，尚未作为包含迁移 `18` 至 `41` 的最终可复现恢复包；旧的二进制 `winpress_full.dump` 同样不能替代迁移 `11` 至 `41`。

## 回退

迁移 11 至 41 会为存量数据库新增表、列、索引、约束、触发器和必要的状态对齐。发生异常时应先停止写入，再从迁移前二进制备份恢复到独立数据库核对，不能在原库上盲目覆盖。新业务写入后不得直接回切旧库处理订单，以免项目或交易状态分叉。

本机演示库可通过 `scripts/verify-local-database-backup-restore.ps1` 验证 PostgreSQL 自定义格式备份能否在隔离临时容器中恢复，并比对关键汇总和当前结构约束。上传文件本体由 `scripts/verify-local-upload-backup-restore.ps1` 恢复到临时 Docker 卷后比对。两项脚本均拒绝非本项目本机演示来源，不连接或改写生产库，也不覆盖生产恢复时限或迁移回退决策。

## Compose 初始化边界

`docker-compose.local-demo.yml` 仅用于本机演示：会加载 `seed.sql`、案例数据、迁移 `17` 以及当前结构所需迁移 `18` 至 `41`，并保留本机验收所需的演示记录。`docker-compose.production.yml` 只加载 `schema.sql`、`02-production-access-control.sql` 和迁移 `13` 至 `16`、`18` 至 `41`；它不自动导入媒体目录、报价、测试账号、客户项目、供应商、案例、演示订单或任何开放 API 密钥。

无论使用哪种初始化方式，媒体数据文件的合法来源、授权范围和对客可见字段都需要单独核验。外部媒体检索接口在未配置有效服务端授权前应保持待配置状态，不能由导入数据或本机案例替代。
